# Upgrading from 9.x to 10.0

Each section below says what changed in EUDIPLO 10.0 and what to do; skip the sections that do not apply to you.

## Before you upgrade

- Upgrade from any 9.x release. On 8.x or older, [upgrade to 9.x first](./index.md#upgrade-guides).
- Follow the [upgrade procedure](./index.md#upgrade-procedure).

## Integrators

### Webhooks and attribute providers: time and size limits, checked redirects

**Changed:** 9.x waited without limit for a webhook or attribute provider, read answers of any size, followed up to 21 redirects without checking their targets against the outbound URL policy, and sent the API key header to every redirect target. 10.0 ends a delivery after 60 seconds, redirects included, and reads at most 5 MiB of the answer. It follows up to 5 redirects (`301`, `302`, `303`, `307`, `308`); each target must pass the [outbound URL policy](../concepts/security-model.md#https-and-tls), and the API key header is only sent to the origin of the configured URL.

**Do:** configure the final URL of the webhook instead of one that redirects, for example `https://` instead of an `http://` URL that redirects, or the trailing slash your framework expects. Answer within 60 seconds; an attribute provider that needs longer answers `{"deferred": true}` ([Deferred issuance](../issuance/deferred-issuance.md)). Keep answers under 5 MiB. Details: [Webhooks](../reference/webhooks.md#delivery).

### Inline webhooks: empty URL, header name or API key rejected

**Changed:** the inline `webhook` of `POST /api/verifier/offer` and a `webhook` claim source in `credentialClaims` of `POST /api/issuer/offer` are validated like stored webhooks. An empty `url`, `auth.config.headerName` or `auth.config.value` now answers HTTP `400`. In 9.x the request was accepted; an empty URL or header name failed later at delivery, and an empty API key was sent as an empty header.

**Do:** send a non-empty `url`, header name and API key, or use `"auth": { "type": "none" }` for a webhook without authentication.

### Registrar: credentials required for a new OIDC or registrar URL

**Changed:** in 9.x, `PATCH /api/registrar/config` with a new `oidcUrl` checked the stored password and client secret against the token endpoint of the new URL, and a new `registrarUrl` received a token obtained with them. Whoever held `registrar:manage` could send the stored credentials to a server of their choice without knowing them. 10.0 answers `400` to a `PATCH` that changes `oidcUrl` or `registrarUrl` unless it also sends `password`, and `clientSecret` if one is stored; a new `registrarUrl` alone is therefore checked against the OIDC endpoint too and can answer `503` when it is unreachable. `POST /api/registrar/config` without `clientSecret` now removes a stored client secret, and so does a configuration bundle or `CONFIG_FOLDER/<tenant>/registrar.json` without it that changes the configuration; 9.x kept it.

**Do:** send `password`, and `clientSecret` if `hasClientSecret` is `true`, in every `PATCH` that changes `oidcUrl` or `registrarUrl`; in the Web Client, enter the password again after changing either URL, and the client secret if the registrar needs one. To drop a client secret, replace the configuration with `POST` without `clientSecret`. Details: [Registrar](../trust/registrar.md).
